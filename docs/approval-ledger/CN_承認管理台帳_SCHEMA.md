# CN_承認管理台帳 正式スキーマ・作成手順・移行方針

最終更新: 2026-10-12

本書は、実行キュー（ExecutionQueue）の人間承認確認に使う SharePoint リスト `CN_承認管理台帳` の正式定義です。
対象サイトは既定サイト（cleannano）です。

## 0. 前提と安全原則

- 承認は**人間が承認台帳に記録する**。AI は承認レコードを作成・更新・削除しない。
- Bridge からの接続は**読み取りのみ**（`SharePointReader.listItems` / `fetchListFields`）。
- 列の内部名は**推測しない**。作成後に実測した値だけを設定に入れる。
- 既存のリスト・列・データは削除、改名、上書きしない。
- SharePoint 上のリスト新規作成は**人間の明示承認後**にのみ行う。
- 本書は設計の確定版であり、本書だけでは実環境は変更されない。

## 1. リスト作成手順書（人間承認後に実施）

前提: 作成前に、既定サイトで `承認管理台帳` を含むリストが存在しないことを確認する（2026-10-12 時点で 0 件）。

1. 既定サイト（hisyoengineer.sharepoint.com/sites/cleannano）を開く。
2. 「新規」→「リスト」→「空のリスト」を選ぶ。
3. 名前を `CN_承認管理台帳` にして作成する。説明は任意（例: 実行キューの人間承認記録）。
4. 次節「2. 列定義」の順に列を追加する。
5. 作成後、リストの URL（listId を含む）と各列の内部名を取得し、実測結果を記録する（「4. 実測手順」）。
6. 承認レコードの入力は人間が行う。入力前に、テスト用の依頼 ID で動作確認を行う場合も、承認状態は人間が判断する。

注意: 手順 2 で「空のリスト」を選ぶこと。既存テンプレートや既存リストを流用しない。

## 2. 列定義

表示名と種類は確定値。内部名は SharePoint が自動付与するため、実測まで未確定とする。

| 表示名 | 種類 | 必須 | 用途 | 承認判定での扱い |
|---|---|---|---|---|
| RequestId | 1 行テキスト | はい | 実行依頼 ID | 依頼と一致する必要あり |
| StepIndex | 数値（整数） | はい | ステップ番号（0 始まり） | 依頼のステップと一致する必要あり |
| ToolName | 1 行テキスト | はい | 対象ツール名 | 依頼のツール名と一致する必要あり |
| ApprovalStatus | 選択肢 | はい | 承認状態 | 値が「承認」の場合のみ承認候補 |
| ApprovedBy | 1 行テキスト | はい | 承認者 | 空の場合は無効 |
| ApprovedAt | 日付と時刻 | はい | 承認日時 | 不正・未来・24 時間超過は無効 |
| Revoked | はい/いいえ | はい | 取消済みか | 「はい」の場合は無効 |

ApprovalStatus の選択肢: 「承認」を必ず含める。その他（例: 「却下」「保留」）は任意。判定上は「承認」のみが有効。

## 3. Approval Ledger マッピング

PR #122（feature/approval-ledger-fetchrows）で定義予定の環境変数と、列・レコードキーの対応は以下のとおり。

| 論理キー（ApprovalRecord） | 表示名 | 環境変数（#122 想定） |
|---|---|---|
| requestId | RequestId | APPROVAL_LEDGER_COL_REQUEST_ID |
| stepIndex | StepIndex | APPROVAL_LEDGER_COL_STEP_INDEX |
| tool | ToolName | APPROVAL_LEDGER_COL_TOOL |
| status | ApprovalStatus | APPROVAL_LEDGER_COL_STATUS |
| approver | ApprovedBy | APPROVAL_LEDGER_COL_APPROVER |
| approvedAt | ApprovedAt | APPROVAL_LEDGER_COL_APPROVED_AT |
| revoked | Revoked | APPROVAL_LEDGER_COL_REVOKED |

リスト特定:

- `APPROVAL_LEDGER_SITE_ID`: 既定サイトの siteId（実測値）
- `APPROVAL_LEDGER_LIST_ID`: `CN_承認管理台帳` の listId（実測値）
- `APPROVAL_LEDGER_LIST_NAME`: 任意。listId が未設定のときのみ使用

判定ルール（ApprovalLedger 側、既存実装どおり）:

- 依頼ID・ステップ番号・ツール名が一致すること
- 状態が「承認」であること
- 取消が「はい」でないこと
- 承認者が空でないこと
- 承認日時が有効で、未来でなく、24 時間以内であること

いずれかの設定が欠けた場合は承認なし（fail closed）。

## 4. 実測手順（作成後に実施、読み取りのみ）

1. `get_sharepoint_columns`（listName=`CN_承認管理台帳`）で列の内部名、表示名、型を取得する。
2. 取得結果の表示名と、本書の表 2 の表示名が一致することを確認する。
3. 内部名を、本書の表 3 の環境変数に設定する。値はこの PR には書かず、デプロイ設定にのみ入れる。
4. 設定後、読み取りで 1 件を確認する（承認レコードがない場合は「該当なし」が正しい結果）。

内部名が表示名と異なる場合も、実測値のみを使う。推測した内部名は設定しない。

## 5. 移行方針（既存リストが後から見つかった場合）

既定サイトに同等のリストが後から見つかった場合は、次の方針で扱う。

1. **既存を優先する。** 新規作成は行わない。
2. 既存リストの列を表 2 と照合する。
   - 表示名が一致する列は、その内部名を環境変数に設定する。
   - 表示名が不足する列は**追加のみ**行う（既存列は変更・削除しない）。追加も人間承認後に行う。
   - 表示名が異なる列は、対応関係を人間に確認してから設定する。推測で対応付けない。
3. 既存データは読み取りのみ。承認状態の変換・一括更新は行わない。
4. 既存リストの承認状態が表 2 の意味と合わない場合（例: 選択肢に「承認」がない）は、承認なし（fail closed）として扱い、人間に判断を委ねる。
5. 移行後、実測（第 4 節）と同じ手順で確認する。

既存の `ledger` 実装は、設定が揃わない限り常に承認なしとなるため、移行途中でも安全側に働く。
