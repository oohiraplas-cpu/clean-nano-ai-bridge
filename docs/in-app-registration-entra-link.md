# 在籍者の登録と Entra ID の紐付け（既存アプリの本人登録 → 承認 → CN_社員台帳）

状態: 設計のみ（DESIGN）。実環境（アプリ・フロー・SharePoint）には何も作成・変更していない。
対象: Microsoft 365 のアカウントをすでに持つ人。アカウント発行前の人は Forms（`new-employee-registration-flow.md`）。

## 確認済み（実環境の読み取り、およびアプリのソースより。個人情報は記録していない）
- アプリに本人登録の画面がある: `S8_UserOnboarding`（入力）→ `S9_UserConfirm`（確認）→ `S10_RegistrationComplete`（完了）。
- 登録先は `CN_本人マイデータ`。社員台帳（`CN_社員台帳`）への書き込みは、この画面にはない。
- `CN_本人マイデータ` の列: `UserUPN`（必須）、`EmployeeID`、`UserType`、`Company`、`Department`、同意の記録（`ConsentAccepted` / `ConsentAt` / `ConsentVersion`）ほか。**`EntraObjectId` の列はない。**
- 現在の件数は 1 件。`EmployeeID` は未入力。
- `UserUPN` の入力欄は、ログイン中のメールを既定値にしているが、**編集できる**（`Update` は入力欄の値）。S9 の重複確認も、入力された値で行っている。
- `CN_社員台帳` には `EntraObjectId`（テキスト）がある。`EmployeeID` と `EntraObjectId` は一意制約なし。アプリは `User().EntraObjectId` で社員台帳を引いて本人確認している。

## 設計上の要点
1. **本人確認に、入力された `UserUPN` を使わない。** 他人の UPN を書き込めてしまうため。フローは、項目の**作成者（登録者）**の情報（SharePoint が自動記録し、利用者が変えられない）を使う。
2. 承認は人間（オーナー）が行う。AI・フロー・Bridge は、承認を代行しない。
3. 社員台帳への書き込みは、承認の後だけ。承認前に書かない。
4. 通知・実行履歴に、住所・生年月日・在留カード番号などの個人情報を出さない。

## フロー（案）
1. トリガー: SharePoint「項目が作成されたとき」（`CN_本人マイデータ`）。
2. **本人の特定**: 作成者のメールアドレスで、Office 365 Users「ユーザーの取得 (V2)」を呼び、`Id`（Entra オブジェクトID）とアカウントの有効状態を取得する（標準コネクタ。ライセンスで追加費用がないかは**要確認**）。取得できなければ、記録して終了。
3. **入力値の照合**: 入力された `UserUPN` が、作成者のメールと一致しなければ、台帳へ進めず、承認者へ「不一致」を通知して終了。
4. **二重処理の防止**: 仮登録台帳（`CN_入社申請_仮登録台帳`）の `FormsResponseId` に `APP-<項目ID>` を入れて検索し、あれば終了（※列の用途の流用。要判断）。
5. **記録**: 仮登録台帳に 1 行追加（`ApprovalStatus` = 承認待ち、`RegistrationStatus` = 未登録、`ApplicantCategory` = `UserType`）。氏名は入れない。
6. **承認**: Teams「アダプティブ カードを投稿して応答を待つ」（宛先: オーナー 1 人）。表示は、氏名と区分のみ。入力欄: 社員ID、所属、入社日、社員区分、承認 / 却下。タイムアウト 7 日。
7. 承認後、`ApprovalStatus` / `ApproverUPN` / `ApprovedAt` を記録する。却下・期限切れは、ここで終了。
8. **重複確認**: `CN_社員台帳` を `EmployeeID` と `EntraObjectId` の両方で検索。どちらか 1 件以上あれば登録せず、`RegistrationStatus` = 重複 にして通知。
9. **正式登録**: `CN_社員台帳` に項目を作成する。`Title` = 氏名、`EmployeeID` = 承認者が入力した社員ID、`Department`、`HireDate`、`EmployeeCategory`、**`EntraObjectId` = 手順 2 で取得した `Id`**、`EmploymentStatus` = 在職（選択肢の文言は要確認）。
10. **本人マイデータへ反映**: `CN_本人マイデータ` の該当項目の `EmployeeID` を更新する（これで S10 の「社員番号」が埋まる）。
11. **結果の記録**: 仮登録台帳の `RegistrationTargetId`（作成された社員台帳の項目ID）と `RegistrationStatus` = 登録済み。失敗時は 失敗 と記録し、承認者へ通知する（詳細・個人情報は載せない）。

登録後は、アプリの既存の本人確認（`User().EntraObjectId` ↔ `CN_社員台帳.EntraObjectId` ↔ `EmployeeID`）が、そのまま通る。

## アプリ側の改修（別の変更。保存・公開は人間の承認が必要）
- `S8` の `UserUPN` 入力欄を、表示専用にする（既定値のまま、書き換えられない）。フローが作成者で照合するので、改修がなくても安全だが、入力ミスを防ぐ。
- `S10` の「社員番号」が、承認前は空であることを、画面の文言で説明する（例: 「承認後に付与されます」）。

## 未確認（実環境で決める）
- `CN_本人マイデータ` を、誰が閲覧・編集できるか（機微情報を含む。最優先で確認）。
- Office 365 Users と Teams のアダプティブ カードが、追加費用なしで使えること。
- 仮登録台帳の `FormsResponseId` を、アプリ経由の登録にも流用してよいか（流用しない場合は、別の列が必要で、列の追加は承認が必要）。
- 社員台帳の選択肢（所属・在籍状態・社員区分）の文言。
- 社員IDの採番ルール（既存の例: `E019` の形式）。

## 動作確認（テスト用の登録で）
1. 自分のアカウントで登録 → 承認 → 社員台帳に 1 行、`EntraObjectId` が `User().EntraObjectId` と一致、本人マイデータの `EmployeeID` が埋まる。
2. `UserUPN` に他人のメールを書いて登録 → 台帳へ進まず、不一致で止まる。
3. 同じ社員IDで再承認 → 登録されない。同じアカウントで 2 回登録 → 登録されない。
4. 却下・期限切れ → 社員台帳に書かれない。
5. 通知・実行履歴に、機微情報が出ていない。
6. テスト用の行は、確認後に無効を示して残す（削除しない）。

## ロールバック
フローをオフにする。登録済みの行は、削除せず、`EmploymentStatus` または `Remarks` で無効を示す。
