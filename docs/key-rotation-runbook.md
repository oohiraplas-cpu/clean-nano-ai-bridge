## 2. 手順（承認後に人間が実施）

1. **新キー登録**: 新しい鍵を生成し、App Service に**新しい変数名**で登録する（例 `CN_MCP_API_KEY_NEXT` は現状のコードでは未使用のため、登録だけでは効かない点に注意）。
2. **新旧併用**: 現行コードは `CN_MCP_API_KEY` のみを見るため、同名での差替えになる。切替の瞬間に旧鍵の利用者は失敗する。これを避けるには、短時間の計画停止（メンテナンス窓）を設けるか、コードに複数鍵の受理（新旧併用）を追加する変更を先に承認を得て入れる。**現状は後者（コード変更）が未実施のため、停止窓を前提とする。**
3. **新キー接続試験**: 更新後、`authentication_check`（認証の有無）と `health_check` を新鍵で呼び、200 を確認する。旧鍵で 401 を確認する。
4. **各接続先の更新**: 上記一覧 1〜7 を順に更新する。各更新の後に接続試験を行う。
5. **旧キー利用ゼロ確認**: App Service の Application Insights / ログで、旧鍵による要求が 0 件になったことを確認する（期間は呼出しの周期に合わせる）。
6. **旧キー失効**: 旧鍵の失効は承認が必要な作業。失効後、旧鍵での要求が 401 になることを確認する。
7. **E2E**: 社員登録の確認フロー（Power Automate → Bridge → 応答）を実行し、成功を確認する。
8. **Rollback 確認**: 問題時は旧鍵を再設定して再起動し、`health_check` と E2E が元に戻ることを確認する。旧鍵が失効済みの場合は、新しい鍵を発行して 1〜4 を繰り返す。

## 3. 禁止事項

- 鍵の値を、チャット・ログ・Git・URL クエリ・監査データに出さない。
- 旧鍵の失効を、利用ゼロの確認前に行わない。
- 本 Runbook の実行を、承認なしに開始しない。
